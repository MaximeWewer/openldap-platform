# openldap

OpenLDAP 2.6 server (StatefulSet) with declarative cn=config bootstrap,
suffix/OU/admin bootstrap, and hooks for downstream sync jobs backed by
openldap-cli.

This subchart is normally installed via the umbrella
[`openldap-platform`](../..). Install it standalone only if you don't need
phpLDAPadmin or Self Service Password sitting next to slapd.

## Requirements

Kubernetes: `>=1.27.0-0`

| replication.replicateConfig | object | `{"checkpoint":"100 10","enabled":true,"sessionLog":100}` | ------------------------------------------------------------------------- cn=config replication.  ON by default (safe on Kubernetes: pods bind their own FQDN, so the URL-form olcServerID matches a listener without any host-networking or topology change - unlike the Docker setup, where this stays opt-in). Only takes effect in HA modes (mirror / multi-master); it is inert in standalone, which has no peer to replicate cn=config with.  Why it matters: without it, anything living in cn=config (olcAccess, overlays, schema, ppolicy, indices) stays on the pod that received the write. The chart's own sync Jobs write cn=config through the ClusterIP Service, which load-balances: with replication OFF, an ACL applied by `acls.sh` lands on ONE arbitrary pod and the others never see it - a failover then serves stale ACLs. Set to false only if you manage cn=config out-of-band or hit an unusual topology constraint.  When enabled, on the WRITABLE StatefulSet only:   - olcServerID switches to the URL form. Mandatory: the `cn=config` entry     itself replicates, so a single-int olcServerID would be overwritten by     the peer's value. Each pod recognises its own line by matching the URL     against one of its listeners hence the slapd `-h` arguments are     pinned to the pod FQDN + 127.0.0.1 instead of the default `ldap:///`.   - a syncprov overlay is added on olcDatabase={0}config (without it the     config DB serves no sync context and every consumer stalls).   - one plain refreshAndPersist olcSyncRepl per writable peer. NOT     delta-syncrepl: the accesslog overlay is attached to {1}mdb only, so     the config DB has no changelog to pull from.   - the bind is the configAdmin rootDN, which bypasses the {0}config ACL.  Read-only replicas never consume the WHOLE cn=config - they would inherit the writable pods' olcMirrorMode: TRUE and stop being read-only. They do get the `cn=schema,cn=config` subtree, and that part is not optional: their syncrepl runs with schemachecking=on, so an entry using an objectClass added at runtime on the writable pool is REJECTED, and that rejection stalls their entire replication stream - silently, including every entry written afterwards. The schema slice keeps them in sync without granting them any of the rest (ACLs, overlays, serverID). Side effect: their {0}config becomes a shadow, so cn=config writes on a read-only pod are refused with `shadow context; no update referral`.  Caveat: olcRootPW of {0}config is hashed per pod (random salt), so the attribute converges to whichever pod wrote last. Same cleartext password either way functionally inert, but expect it to differ from the local hash after the first sync. |
